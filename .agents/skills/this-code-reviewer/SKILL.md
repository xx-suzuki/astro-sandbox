# this-code-reviewer

## レビュー優先順位

1. バグ
2. 回帰リスク
3. 本プロジェクトの規約違反
4. 最適化
5. 可読性
6. 保守性
7. テスト不足

## 実行フロー

1. プロジェクト規約を確認する
   - `README.md` と `AGENTS.md` を確認する
   - 判断根拠が必要な場合は該当箇所を確認する

2. レビュー対象を確認する
   - **ファイル指定の場合**: 指定ファイルの実装内容を把握する
   - **差分レビューの場合**: `git diff` または `git diff --staged` で変更を確認する
   - 変更意図があれば先に確認する

3. 影響範囲を最小限で確認する
   - 関連シンボル・参照元/参照先・対応テストの有無を確認する
   - 推測ではなく根拠が取れる範囲で指摘する

4. 優先順位に沿って指摘を抽出する
   - バグと回帰リスクを最優先で列挙する
   - 指摘がない場合はその旨を明記する
   - プロジェクト固有の確認観点は `references/review-checklist.md` を参照する

5. 各指摘に改修案を付ける
   - 何が問題か（内容の解説）
   - なぜ問題か（影響/再現条件）
   - どう直すか（具体的な改修案）
   - 指摘には対象ファイルと行番号を含める
   - 判断に必要な情報が足りない場合は、断定せず確認事項として扱う

6. テスト観点を提示する
   - 不足テストの有無を判断する
   - 必要なテストケースを具体的に提案する

## 出力フォーマット

**Findings**（重大度順）
- `severity:` High / Medium / Low
- `file:` 対象ファイル
- `line:` 指摘箇所
- `issue:` 問題点
- `explanation:` 内容の解説
- `proposal:` 改修案

**Test**
- 追加/修正すべきテスト観点

**Open Questions**（必要な場合のみ）
- 判断にユーザー確認が必要な事項

**Summary**
- 全体所見（1〜3 行）

## 運用ルール

- 指摘は具体的な根拠があるものだけを出す
- 根拠が曖昧な場合は推測で断定せず Open Questions に回す
- スタイル指摘より動作不良・回帰を優先する
- 改修案では過度なフォールバックを増やさず、不要な後方互換を持たせない案を優先する
- レビュー依頼では原則としてファイルを変更しない
- ユーザーが実装修正を明示した場合のみ、変更方針を示してから修正する

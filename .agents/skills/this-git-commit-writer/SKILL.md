# this-git-commit-writer

## 入力前提

- 作業ツリーに未コミット変更がある
- このリポジトリのコミット規約が `AGENTS.md` に記載されている
- コミット書式は既存の `git log` 履歴を最優先で参照する

## 実行フロー

1. 変更状況を把握する
   - `git status --short`
   - `git diff --name-only` / `git diff --cached --name-only`
   - `git diff` / `git diff --staged`
   - 未追跡ファイルも確認し、コミット候補に含めるか分類する

2. コミット規約を収集する
   - `AGENTS.md` の Git 運用・コミットメッセージセクションを最優先で確認する
   - `git log --oneline -n 20` で実際に使われている書式を確認する
   - 過去運用を根拠にする場合は、該当コミットハッシュやファイルパスを提示する

3. 差分を意味単位でクラスタリングする
   - 1 コミット 1 目的を原則に分割する
   - 実装とそのテストは同一コミットを基本とする
   - 無関係な整形・設定変更・ドキュメント変更は必要に応じて分離する

4. 各コミット候補を作成する
   - メッセージ形式は Conventional Commits（`<type>(<scope>): <subject>`）を使う
   - `type` / `scope` の選択は `references/commit-types.md` を参照する
   - subject は英語・小文字始まり・命令形で書く
   - 形式に迷う場合は `git log` の直近コミット（`3693c13` 以降）の書式に合わせる
   - 各候補に `主題` / `対象ファイル` / `推奨メッセージ` / `提案理由` を含める

5. 妥当性チェック
   - メッセージと差分の整合を確認する
   - 破壊的変更や副作用を明記する
   - ユーザーが分割順・scope 制約を明示した場合は最優先で従う

## 出力フォーマット

推奨案（分割有無）を一文で提示後、コミット案を番号付きで提示する。

各案の固定表示:
- `message:` コミットメッセージ
- `topic:` 主題
- `files:` 対象ファイル一覧
- `why:` 提案理由
- `evidence:` 根拠（コミットハッシュ・AGENTS.md 該当箇所など）

## 判断ルール

- 変更の意図が異なるなら分割する
- 依存関係が強く分離困難なら 1 コミットにまとめる
- テストは原則、対象実装と同じコミットへ含める
- 無関係な整形は別コミットに分離する
- `.agents` 配下と `AGENTS.md` の変更は `agents` scope として分ける
- 依存追加・更新は `pnpm-lock.yaml` を同一コミットに含める（`chore(deps)`）
- 生成物（`dist/` `.tmp/` `report-w3c.txt` `stats.html` `coverage/` および `.gitignore` 済みの生成 SCSS / 型定義）はコミット候補から除外する

## 注意事項

- コミット提案のみの指示なら「提案のみ」を返す
- 実コミット指示があるときだけ `git add` / `git commit` を実行する
- 実コミット前に対象ファイルとメッセージをユーザーへ確認する
- テスト結果はコミットメッセージや PR 本文に記載しない（秘匿情報流出防止）
- テスト失敗時はコミットせず、原因特定と修正提案を優先する

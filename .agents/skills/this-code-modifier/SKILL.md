# this-code-modifier

## 実行フロー

1. 要件を確定する
   - 対象ファイルと期待動作を特定する
   - 変更対象外（触らない範囲）を明確にする
   - 判断に必要な情報が不足している場合は更新せず、ユーザーへ確認する

2. 現状を把握する
   - `README.md` と `AGENTS.md` を確認する
   - 関連コードと既存テストを確認する
   - 失敗条件・再現手順を作る

3. 変更案を提示して実行可否を確認する（条件付き）
   - 変更方針・対象ファイル・想定影響を簡潔に提示する
   - ユーザーから即時実装の明示指示がない場合のみ、実装前に確認する
   - 即時実装の指示があっても、仕様判断が必要・影響範囲が大きい・破壊的変更の可能性がある場合は確認する

4. 実装する
   - 要件に沿って最小差分で修正する
   - 既存スタイルと命名を維持する
   - ついで修正は避け、目的に直結する変更に限定する
   - DRY を保ち、同種ロジックの重複実装を避ける
   - 設定値は `project.config.ts` に集約し、各所へハードコードしない
   - パスは `@/*` `@scripts-node/*` `@root/*` のエイリアスで書く
   - SCSS は FLOCSS のレイヤーとプレフィックス（`l-` / `c-` / `p-` / `u-`）に従い、同階層の `_index.scss` へ `@use` を追加する
   - 生成物（`.tmp/` `dist/` および `.gitignore` 済みの生成 SCSS / 型定義）は直接編集せず、生成元を修正する
   - import 順・オブジェクトキー順は perfectionist が自動整列するため手で並べ替えない

5. 検証する
   - 変更後は `pnpm format` → `pnpm check` → `pnpm test:scripts` の順で実行する
   - Astro / SCSS を変更した場合は `pnpm check:markup` を追加する
   - マークアップ検証まで必要な場合のみ `pnpm report:w3c` を実行する（内部で検証用ビルドまで行う）
   - 失敗した場合は原因を特定し、修正して再検証する

6. `$this-code-reviewer` でレビューする
   - 変更した production ファイルを `$this-code-reviewer` でレビューする
   - 指摘がある場合は対応要否を判断し、必要なものは修正して再検証する
   - 今回の目的外の指摘は勝手に修正せず、確認事項として報告する

7. 結果を報告する
   - 変更内容
   - 検証コマンドと結果
   - `$this-code-reviewer` のレビュー結果
   - 実行できなかった検証と理由
   - 残課題（あれば）

## 入力解釈ルール

- 「修正して」: 不具合や不整合を期待動作へ合わせる
- 「調整して」: 挙動や構造を大きく変えずに整える
- 「最適化して」: 計測可能な改善（性能・可読性・重複削減）を優先する
- 「バグ修正して」: 原因と修正内容の解説を必ず含める
- 指定ファイルのレビューのみが目的なら `$this-code-reviewer` を使い、原則として実装変更しない

## 出力フォーマット

- 要約（何を直したか）
- 変更ファイル一覧
- 実行した検証と結果
- `$this-code-reviewer` のレビュー結果
- 実行できなかった検証（必要時のみ）
- 確認事項（必要時のみ）
- 次アクション（必要時のみ）
